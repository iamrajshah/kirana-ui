Evidence before opinion

Grounding Context

Already strong

Responsive Ionic shell, role protection, lazy loading, four-language coverage, walk-in billing, Cash/UPI quick checkout, idempotency, draft invoices and payment recovery.

Visible friction

The owner dashboard is aggregate-only, the Billing scan affordance is disconnected, and draft resumption is buried in Invoices.

Reusable substrate

Stock movements, suppliers, purchases, customer contacts, orders, ledger records and draft invoices reduce the cost of the strongest next ideas.

Important constraint

Railway/MySQL remain stopped. Contract and UI work can use mocks, but database-backed features need a disposable migrated MySQL environment before end-to-end claims.

I1. Owner Decision Inbox

Owner decisionsConfidence 94%Complexity Medium
Description
Replace aggregate-only owner oversight with three ranked, record-linked decisions: money to collect, stock likely to run out, and counter activity needing review. Every item explains why it matters now and provides one primary action plus snooze, assign, or dismiss-with-reason.
Basis
direct: the current dashboard service returns six aggregate values with no invoice, customer, supplier, product, or staff identifiers. The existing owner demo already frames Today as the three things needing attention.
Rationale
This changes Kirana from software containing reports into a daily operating assistant. It also gives future shifts, reorders, held bills and collections one owner-facing destination instead of separate dashboards.
Downsides
Requires new exception contracts and careful ranking. Poor recommendations will erode trust, so early rules must be explainable and owner feedback must be captured.
2

I2. Ambient Scan-to-Catalog

CheckoutConfidence 96%Complexity Small–Medium
Description
Connect camera, keyboard-wedge, manual-code and search input to one Billing lookup path. Known products add instantly; unknown barcodes become a small non-blocking resolution card that an OWNER or MANAGER can approve, improving the tenant catalog for the next scan.
Basis
direct: Billing renders a scan button without a handler, while a working Capacitor scanner and local-first barcode lookup already exist. Barcode creation is already limited to OWNER/MANAGER.
Rationale
This is the clearest immediate counter win and turns a current dead affordance into a compounding catalog-quality loop.
Downsides
Desktop scanner focus and unknown-product permissions need explicit behavior. External barcode matches remain suggestions, never automatic product truth.
3

I3. Held-Bill Relay

CheckoutConfidence 93%Complexity Medium
Description
Promote DRAFT invoices into visible cashier work packets with customer cue, amount, item count, age, source, counter, holder and version. A short edit lease provides read-only visibility elsewhere and an explicit manager takeover instead of silent last-write-wins behavior.
Basis
direct: drafts can already be saved, updated, resumed and finalized, but resumption is buried under invoice filters and the model has no ownership or collision semantics.
Rationale
The same relay can later receive interrupted sales, WhatsApp lists and customer-app orders, making it a reusable continuity primitive rather than another cart store.
Downsides
Requires durable actor/version metadata and lease expiry rules. Cross-counter concurrency must be tested against real MySQL before claiming production readiness.
4

I4. 90-Second Shift Close

Cash accountabilityConfidence 92%Complexity High
Description
Model cash as custody: opening float, named shift, cash sales/refunds, paid-in/out events, blind closing count, expected-versus-actual variance, explanation and owner approval. UPI/Card/Bank remain visible for reconciliation but never inflate physical drawer cash.
Basis
direct + external: Kirana already groups daily payments by mode but lacks shifts and durable payment actor attribution. Bank-teller session patterns map directly to expected cash, blind count, variance and supervisory sign-off.
Rationale
This gives the owner an end-of-day proof rather than another sales report and creates the trustworthy attribution required for staff performance.
Downsides
Needs new server models and migration. The experience must adapt for a solo owner so opening/closing ceremony does not become enterprise-style busywork.
5

I5. Reorder Confidence Queue

ReplenishmentConfidence 88%Complexity Medium–High
Description
Rank reviewable replenishment suggestions by on-hand quantity, sales movement, last purchase, supplier history, urgency and confidence. Approved lines become editable supplier-grouped purchase drafts; the system never places an order autonomously.
Basis
direct: thresholds, stock movements, top-selling quantities, suppliers, purchase history and purchase-cart creation already exist. The missing data—lead time, pack size, preferred supplier—can be shown as confidence limits.
Rationale
It changes low-stock warnings into decisions about scarce cash while keeping the shopkeeper in control and making every suggestion explainable.
Downsides
Early recommendations will be approximate. Seasonal demand, informal supplier terms and missing purchase history must reduce confidence rather than be guessed.
6

I6. WhatsApp List Compiler

Assisted ordersConfidence 82%Complexity High
Description
Preserve the incoming text or photo, propose product/variant matches, flag uncertain quantities and substitutions, and require staff review before producing one held bill. Start with paste/import or a structured link; full WhatsApp API transport can follow after the workflow proves useful.
Basis
direct + external: tenant-scoped customer phones and customer cart → order → draft-invoice conversion already exist. WhatsApp commerce is common in India, but Kirana currently has no transport, consent, template or message log.
Rationale
The valuable automation is eliminating retyping without letting unstructured chat bypass stock, customer, invoice or tenant controls.
Downsides
Staff-side order creation and matching require new contracts. Full outbound reminders need consent, approved templates, delivery logs and provider cost analysis.
7

I7. Bounded Emergency Offline Mode

Checkout continuityConfidence 86%Complexity Very High
Description
Permit only clearly safe offline actions—paid-in-full walk-in sales against a local catalog snapshot—and show every local envelope as queued, syncing, conflicted or completed. Reconnect replays through stable idempotency identities; credit, returns and stock-sensitive administration remain unavailable.
Basis
direct + external: invoice/payment idempotency exists, while network failure currently becomes a generic notification and no local queue exists. Mature offline POS systems expose constrained modes and visible unsynced work.
Rationale
This preserves the revenue path during outages without pretending the full POS and ledgers can safely operate offline.
Downsides
Requires secure local storage, device identity, catalog snapshots, transactional outbox semantics, conflict handling and substantial reconnection testing. It should follow—not precede—the simpler operational primitives.

Direction, not implementation plan

Suggested Sequence

Directional only — this shows sequencing logic, not committed scope or an implementation specification. The quick scan fix can land independently; the Owner Decision Inbox is the strongest next product conversation.
